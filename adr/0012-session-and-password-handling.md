# ADR 0012 — Session and Password Handling

Date: 2024-Q3 (first deliverable)
Decision Maker: ShareNet 2.0 build orchestrator

## Status

**Accepted.** This decision fixes the password hashing, session
storage, cookie handling, expiration, account-disable, and audit-
logging strategy for human accounts in the first deliverable.

## Context

`spec/14-security.md` §1 ("Human Identity (Account) Security")
mandates: (1) password hashing with bcrypt (cost ≥ 12) or Argon2id;
(2) no password in JWT payload; (3) TOTP-based 2FA for operator
accounts; (4) cryptographically random session tokens (≥ 256 bits)
stored server-side with a binding to UserId and an expiration; (5)
secure cookies (`HttpOnly`, `Secure`, `SameSite=Strict` or `Lax`);
(6) session expiration (8h inactivity, 24h absolute).

`spec/14-security.md` §2 mandates server-side role checks and
immediate session invalidation on account disable. §5 mandates audit
entries for every authorization decision, session lifecycle event,
account disable, revocation list mutation, settlement, and issuance.
§10 mandates no custom crypto, constant-time comparisons for
secrets, and CSPRNG for all key generation and nonces.

The first deliverable needs a session system compatible with the
Next.js Node runtime that plays well with the waitlist-before-account
flow (ADR 0008), the demo-account-isolation flow (ADR 0009), and the
audit-log hash chain, can be revoked immediately on account disable,
and does not require horizontal scaling beyond the first deliverable.

## Decision

**Password hashing.** Use bcrypt with cost factor 12. The password
hash is stored in the `User` table's `passwordHash` column. The
hash is computed at account creation (after waitlist approval, per
ADR 0008) and at every password change. The plaintext password is
NEVER stored in any form. bcrypt is provided by `bcryptjs` (per
Task 1's installed dependency set). 2FA is OPTIONAL for `USER`
role and REQUIRED for `OPERATOR` and `ADMIN` roles, implemented as
TOTP via `otplib`. The TOTP secret is stored encrypted at rest.

**Session storage.** Sessions are stored server-side in a
`Session` table. The schema:

```
Session {
  id              String   @id @default(cuid())
  token           String   @unique   // 32-byte random, base64url
  userId          String             // FK to User
  isDemo          Boolean  @default(false)  // per ADR 0009
  createdAt       DateTime @default(now())
  lastUsedAt      DateTime @default(now())
  expiresAt       DateTime            // absolute expiry
  idleExpiresAt   DateTime            // sliding inactivity expiry
  ip              String?             // last-seen IP (for audit)
  userAgent       String?            // last-seen UA (for audit)
  revokedAt       DateTime?           // set when explicitly revoked
  user            User     @relation(fields: [userId], references: [id])
}
```

The token is 32 bytes (256 bits) generated by Node's
`crypto.randomBytes(32)` and base64url-encoded. The token is the
ONLY thing stored in the cookie; the server looks up the session
row by token on every request.

**Cookie.** Cookie name: `sharenet_session` (demo variant
`sharenet_demo_session` per ADR 0009). Attributes: `HttpOnly: true`,
`Secure: true` in production (HTTPS only), `SameSite=Lax` (top-level
navigation, blocks CSRF on non-GET), `Path=/`, `Max-Age` matching
`idleExpiresAt` (refreshed every request, sliding window). No `Domain`
attribute (cookie is host-only).

**Expiration.** Sliding window of 8h inactivity (`idleExpiresAt`),
absolute 24h max (`expiresAt`). Sliding resets `idleExpiresAt` on
every authenticated request but NOT `expiresAt`. A session idle for
8h OR older than 24h is rejected; the user must re-authenticate.

**Account disable.** When an admin disables a User
(`User.disabled = true`): (1) all `Session` rows for that `userId`
are updated to set `revokedAt = now()`; the next request presenting
any of those sessions is rejected with `401`. (2) An audit-log
entry is recorded with `event = "account_disabled"`,
`actor_userId` = the admin, `target_userId` = the disabled user.
(3) The disabled user's `disabledAt` and `disabledBy` columns are
set for forensic reference.

**Authorization middleware.** Every authenticated endpoint runs
through a middleware that: (1) reads the `sharenet_session` cookie;
(2) looks up the `Session` row by token; (3) checks
`Session.revokedAt IS NULL`, `Session.expiresAt > now()`,
`Session.idleExpiresAt > now()`, and `User.disabled = false`; (4) on
failure returns `401` and clears the cookie; (5) on success refreshes
`Session.idleExpiresAt` and attaches `session` and `user` to the
request context; (6) checks role (endpoint declares required role);
(7) demo check (per ADR 0009): if `session.isDemo = true`, endpoints
marked `realAdminOnly` reject the request even if the demo user has
admin role.

**Audit logging.** Every auth event is logged in the `AuditLog`
table with a hash chain (`prev_hash = SHA-256(prev_entry)` per
`spec/14-security.md` §5). Events: `login_success`, `login_failure`,
`logout`, `session_expired`, `account_disabled`, `role_changed`,
`session_revoked`. Audit-log reads are admin-only. The hash chain is
verified by a nightly job that recomputes the chain and asserts
equality.

## Consequences

- **Server-side session store.** Cannot scale horizontally
  without a shared session store (Postgres in production per ADR
  0001, or Redis for sub-ms lookups). SQLite is sufficient for the
  first deliverable's single-process workload.
- **Session token is opaque.** No JWT; the server is the source of
  truth for session validity. Revocation is trivial.
- **bcrypt cost 12 is ~250ms per hash on commodity hardware.**
  Acceptable for login and account creation.
- **Cookies are HttpOnly and SameSite=Lax.** Cross-site top-level
  navigation works; cross-site POST does not carry the cookie (CSRF
  protection).
- **Sliding window of 8h.** A user idle for 8h is logged out. An
  attacker who steals a cookie has at most 8h inactivity (or 24h
  absolute) to use it.
- **Account disable is immediate.** A disabled user's sessions
  are revoked in the same transaction. The next request is rejected
  with `401` and the cookie is cleared.
- **Audit log is the forensic record.** Every auth event is
  recorded; the hash chain makes tampering detectable. Retention
  is 90 days.
- **2FA for operator/admin accounts.** Adds friction but is
  mandated by `spec/14-security.md` §1.3.
- **No password in any token.** The session cookie contains only
  the opaque token. The session row contains only the bcrypt hash.
  Plaintext passwords exist only in the request body of
  `/api/auth/login` and `/api/auth/change-password`, and are not
  logged.

## Alternatives Considered

1. **JWT (stateless).** Rejected — `spec/14-security.md` §1.2 forbids
   passwords in JWT, and stateless JWT revocation is hard.
2. **NextAuth (Auth.js).** Considered — would be acceptable but adds a
   heavy abstraction, makes audit-log integration harder (NextAuth's
   session model is opaque), and the custom session is leaner.
3. **Argon2id instead of bcrypt.** Considered — Argon2id is the modern
   recommendation. Rejected because `bcryptjs` is already installed
   and proven; Argon2id would require a native binding or WASM module
   (per ADR 0002 we avoid both).
4. **Redis for session store.** Rejected — adds an external
   dependency. SQLite is sufficient for the first deliverable.
5. **`SameSite=Strict` instead of `Lax`.** Considered — `Strict`
   blocks all cross-site cookie carriage, including top-level
   navigation from a link. `Lax` is the right trade-off.
6. **No 2FA for the first deliverable.** Rejected — `spec/14-security.md`
   §1.3 mandates 2FA for operator accounts.
