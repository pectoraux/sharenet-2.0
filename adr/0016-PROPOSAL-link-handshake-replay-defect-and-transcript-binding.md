# ADR-0016 — RESOLVED: Link Handshake Transcript Binding and Replay Protection

**Date:** 2026-08-16 (original proposal); 2026-08-16 (revised); 2026-08-16 (RESOLVED by Principal Architect)
**Status:** RESOLVED — Principal Architect approved the canonical 3-message handshake design via the frozen protocol decisions in the GATE roadmap (§B). Implementation authorized.

## Resolution

The Principal Architect has approved the following canonical 3-message handshake
design. This ADR is now CLOSED. The implementation is authorized under GATE-03.

### Approved design (frozen in roadmap §B)

**Transcript framing:**

```
transcript_hash = BLAKE3-256(
  utf8("SHARENET/LINK/TRANSCRIPT/1")
  || u32be(length(message_1)) || message_1
  || u32be(length(message_2)) || message_2
  || ...
)
```

**Possession payload (what each party signs):**

```
possession_payload = utf8(role-specific domain tag)
  || transcript_hash           (32 bytes)
  || directional_link_id_bytes (32 bytes)
  || peer_generated_challenge  (32 bytes)
  || role_byte                 (1 byte: 0x01 = INITIATOR, 0x02 = RESPONDER)
```

**Domain tags:**
- `SHARENET/LINK/POSSESSION/INITIATOR/1`
- `SHARENET/LINK/POSSESSION/RESPONDER/1`

**Transcript domain tag:**
- `SHARENET/LINK/TRANSCRIPT/1`

**Three-message flow:**

1. Initiator → Responder, `Initiate`:
   - canonical advertisement bytes for A
   - `link_nonce_A`: 16 random bytes
   - `challenge_for_B`: 32 random bytes

2. Responder → Initiator, `Accept`:
   - canonical advertisement bytes for B
   - `link_nonce_B`: 16 random bytes
   - `challenge_for_A`: 32 random bytes
   - `proof_B`: Ed25519 signature by B over B's possession payload

3. Initiator → Responder, `Confirm`:
   - `proof_A`: Ed25519 signature by A over A's possession payload

**Rules:**
- Each party signs the challenge generated by the peer, never its own.
- A `LINK_UP` record exists only after both proofs verify.
- `ADV_VERIFIED` is not routable.

## Original PROPOSAL (preserved for audit trail)

### 1. Defect summary

The current two-message handshake (`reference/transport/handshake.ts`) verifies
signed NodeAdvertisements in both directions but does NOT prove fresh possession
of the signing key bound to the connection transcript. A captured advertisement
is replayable until its `expiry` timestamp (up to 24 hours later).

The exchange therefore establishes `ADV_VERIFIED` (advertisement-verified), NOT
`LINK_UP` (authenticated). See `spec/04-links.md` §4 (corrected state machine).

## 2. Goals of the revised proposal

- Distinguish handshake challenges from LinkId nonces.
- Define exact role ownership for every nonce.
- Ensure each party signs the challenge issued by the peer.
- Define a canonical transcript byte representation and transcript-hash algorithm.
- Define exact domain-separation tags.
- Bind each possession proof to role, both NodeIds, both fresh challenges,
  and the connection transcript.
- Define replay-storage scope and expiration.
- Include valid, tampered, replayed, wrong-role, and wrong-LinkId vector
  requirements.

## 3. Nonce taxonomy (challenges vs. LinkId nonces)

There are TWO distinct nonce categories in the handshake. They MUST NOT be
conflated:

### 3.1 LinkId nonces

- **Purpose:** bind the LinkId to a specific handshake instance (prevent
  LinkId reuse across reconnects).
- **Ownership:** each party generates its OWN LinkId nonce. The initiator
  generates `link_nonce_A`; the responder generates `link_nonce_B`.
- **Usage:** input to `deriveLinkId(localNodeId, remoteNodeId,
  local_link_nonce, remote_link_nonce)`.
- **NOT signed directly:** the LinkId nonces are part of the transcript hash
  (see §5) but are NOT the challenge that the peer signs.

### 3.2 Handshake challenges

- **Purpose:** prove fresh possession of the signing key by requiring each
  party to sign a challenge it did NOT generate.
- **Ownership:** each party generates a challenge FOR THE PEER to sign.
  - The initiator generates `challenge_for_B` — a 32-byte random value that
    the responder MUST sign.
  - The responder generates `challenge_for_A` — a 32-byte random value that
    the initiator MUST sign.
- **Rule:** a party NEVER signs its OWN challenge. The initiator signs
  `challenge_for_A` (generated by the responder). The responder signs
  `challenge_for_B` (generated by the initiator).

## 4. Role ownership table

| Nonce / Challenge | Generated by | Signed by | Purpose |
|--------------------|-------------|-----------|---------|
| `link_nonce_A` | Initiator (A) | (not signed directly; part of transcript hash) | LinkId binding |
| `link_nonce_B` | Responder (B) | (not signed directly; part of transcript hash) | LinkId binding |
| `challenge_for_B` | Initiator (A) | Responder (B) signs this | Proves B possesses its signing key |
| `challenge_for_A` | Responder (B) | Initiator (A) signs this | Proves A possesses its signing key |

## 5. Canonical transcript byte representation

The transcript is the concatenation of all handshake messages exchanged so
far, in the order they were sent, each prefixed by its canonical-CBOR
encoding. The transcript hash is BLAKE3-256 of the transcript bytes.

### 5.1 Transcript construction

```
transcript = canonical_cbor(msg_1) || canonical_cbor(msg_2) || ...
transcript_hash = BLAKE3-256(transcript)
```

At each signing step, the signer includes the `transcript_hash` computed
from ALL prior messages. This binds the signature to the exact sequence of
bytes exchanged, preventing transcript substitution.

### 5.2 Message sequence (3-message handshake)

```
Step 1: A → B: InitiateMessage
  { advertisement: adv_A,
    link_nonce_A: 16 bytes,
    challenge_for_B: 32 bytes }

Step 2: B → A: AcceptMessage
  { advertisement: adv_B,
    link_nonce_B: 16 bytes,
    challenge_for_A: 32 bytes,
    possession_proof_B: Ed25519 signature }

Step 3: A → B: PossessionConfirmMessage
  { possession_proof_A: Ed25519 signature }
```

### 5.3 Transcript hash at each step

- At step 2 (B signs): `transcript_hash = BLAKE3-256(canonical_cbor(msg_1))`
  — includes only the InitiateMessage.
- At step 3 (A signs): `transcript_hash = BLAKE3-256(canonical_cbor(msg_1) || canonical_cbor(msg_2))`
  — includes both prior messages.

## 6. Domain-separation tags

Each possession-proof signature is over a domain-separated payload:

```
possession_proof_payload = utf8(domain_tag)
  || transcript_hash       (32 bytes)
  || link_id_bytes         (32 bytes — the LinkId hash, not the text form)
  || challenge             (32 bytes — the challenge issued by the peer)
  || role_byte             (1 byte: 0x01 = INITIATOR, 0x02 = RESPONDER)
```

### Registered domain tags

| Tag | Purpose | Used by |
|-----|---------|---------|
| `SHARENET/LINK/POSSESSION/INITIATOR/1` | Initiator's possession proof (signs `challenge_for_A`) | Step 3 |
| `SHARENET/LINK/POSSESSION/RESPONDER/1` | Responder's possession proof (signs `challenge_for_B`) | Step 2 |

These tags are FROZEN per spec/14-security.md §4 and MUST NOT be reused for
any other signature domain.

## 7. Possession proof binding

Each possession proof binds to:

1. **Role:** the `role_byte` distinguishes INITIATOR (0x01) from RESPONDER (0x02).
   A proof signed with the wrong role MUST be rejected.
2. **Both NodeIds:** the `link_id_bytes` is derived from
   `(localNodeId, remoteNodeId, link_nonce_A, link_nonce_B)`, which transitively
   binds to both NodeIds. A proof signed over a different LinkId MUST be rejected.
3. **Both fresh challenges:** the `challenge` field is the challenge issued by
   the peer. The transcript_hash includes both `challenge_for_A` and
   `challenge_for_B` (they are in msg_1 and msg_2 respectively). A proof
   signed over a different challenge MUST be rejected.
4. **Connection transcript:** the `transcript_hash` binds to the exact
   sequence of bytes exchanged. A proof signed over a different transcript
   (e.g. a replayed message from a different connection) MUST fail because
   the transcript_hash differs (the LinkId nonces differ).

## 8. Replay-storage scope and expiration

### 8.1 What is stored

Each party MUST maintain a replay cache of recently-seen challenges it
generated. The cache stores:

```
{ challenge: 32 bytes, generated_at: unix_ms, used: boolean }
```

### 8.2 Scope

- **Per-node, in-memory only.** The replay cache is NOT persisted to disk
  and NOT shared across nodes.
- **Per-challenge:** each challenge is single-use. Once a party receives a
  valid possession proof for a challenge it issued, the challenge is
  marked `used: true` and MUST NOT be accepted again.

### 8.3 Expiration

- Challenges expire after 5 minutes (300 seconds) from generation.
- Expired challenges are purged from the cache.
- An expired challenge's possession proof MUST be rejected with
  `reason="challenge_expired"`.
- A replayed challenge (same 32 bytes seen twice with `used: true`) MUST be
  rejected with `reason="challenge_replayed"`, and the connection MUST be
  closed immediately.

### 8.4 Abuse detection

- 3 replay attempts within 60 seconds from the same peer NodeId: the peer
  is added to a temporary denylist (5 minutes). Future connection attempts
  from that NodeId are refused at the TCP layer.

## 9. Failure handling

| Failure | Action |
|---------|--------|
| Advertisement verification fails (signature, binding, timestamp, expiry) | Close socket, record `LINK_DOWN` with `reason="adv_verification_failed"`, no `ADV_VERIFIED` or `LINK_UP` |
| Possession proof signature invalid | Close socket, record `LINK_DOWN` with `reason="possession_proof_invalid"`, increment abuse counter |
| Possession proof role wrong | Close socket, record `LINK_DOWN` with `reason="wrong_role"`, increment abuse counter |
| Possession proof LinkId mismatch | Close socket, record `LINK_DOWN` with `reason="wrong_link_id"`, increment abuse counter |
| Challenge expired | Close socket, record `LINK_DOWN` with `reason="challenge_expired"` |
| Challenge replayed | Close socket, record `LINK_DOWN` with `reason="challenge_replayed"`, increment abuse counter, add to denylist after 3 attempts |

## 10. Required test vectors

The following vectors MUST be authored as frozen conformance artifacts
before the implementation is considered complete. Each vector is a JSON
file under `conformance/vectors/`.

### 10.1 V-LINK-HANDSHAKE-001: valid handshake

A complete 3-message handshake producing `LINK_UP` on both sides. The vector
includes:
- Both keypairs (seed + public key)
- Both link nonces
- Both challenges
- Both possession proofs (with exact signature bytes)
- The transcript hash at each step
- The final LinkId

### 10.2 V-LINK-HANDSHAKE-002: tampered possession proof

Same as V-LINK-HANDSHAKE-001 but with one bit flipped in `possession_proof_B`.
Expected result: `possession_proof_invalid`, connection closed, no `LINK_UP`.

### 10.3 V-LINK-HANDSHAKE-003: replayed AcceptMessage

A valid `AcceptMessage` captured from a prior connection (different
`link_nonce_A`) is replayed in a new connection. Expected result:
`transcript_hash` mismatch (the transcript includes a different
`link_nonce_A`), possession proof fails, connection closed.

### 10.4 V-LINK-HANDSHAKE-004: wrong role

The responder's possession proof is signed with `role_byte = 0x01`
(INITIATOR) instead of `0x02` (RESPONDER). Expected result:
`wrong_role`, connection closed.

### 10.5 V-LINK-HANDSHAKE-005: wrong LinkId

The responder's possession proof is signed over a different `link_id_bytes`
(one where the NodeIds are swapped). Expected result: `wrong_link_id`,
connection closed.
