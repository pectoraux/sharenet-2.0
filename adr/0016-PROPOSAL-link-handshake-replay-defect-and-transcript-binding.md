# ADR-0016 — PROPOSAL: Link Handshake Replay Defect and Transcript Binding

**Date:** 2026-08-16
**Status:** PROPOSAL — awaiting Principal Architect decision. **Do not implement.**

## Context

The current Phase 3 two-message handshake (`reference/transport/handshake.ts`)
verifies signed NodeAdvertisements in both directions:

```text
Initiator (A)                       Responder (B)
-----------                         -------------
1. SEND InitiateMessage(adv_A)  →
                                   2. verifyAdvertisement(adv_A)
                                       IF OK → SEND AcceptMessage(adv_B)
   ←
3. verifyAdvertisement(adv_B)
   IF OK → LINK_UP (both sides)
```

**Defect:** the handshake verifies that each peer **possessed the signing key
at some point in the past** (when the advertisement was signed), but it does
NOT prove that the peer **currently possesses the signing key bound to this
specific connection transcript**.

A passive network observer who captures a single InitiateMessage (or
AcceptMessage) can replay it later in a new TCP connection. The replayed
advertisement's signature will still verify (the signature is valid
indefinitely until the advertisement's `expiry` timestamp). The responder
will issue an AcceptMessage and enter LINK_UP with an attacker who never
proved possession of the advertised NodeId's private key.

This means the current handshake is **NOT an authenticated link** in the
cryptographic sense required by spec/04 §3.2 ("peer authentication →
LinkUp"). It is an **advertisement-verification exchange**, which is a
weaker property.

## Exact current (defective) behavior

```typescript
// reference/transport/handshake.ts
export function verifyPeerHandshake(msg, expectedNodeId?, now?) {
  const adv = msg.advertisement;
  const v = verifyAdvertisement(adv, now);  // spec/03 §5 checks
  if (!v.ok) return { ok: false, ... };
  if (expectedNodeId && adv.nodeId !== expectedNodeId) return { ok: false, ... };
  return { ok: true, advertisement: adv, ... };
}
```

The `verifyAdvertisement()` call checks:
1. signature over canonical-CBOR body
2. identity binding (NodeId == deriveNodeId(publicKey))
3. timestamp ± 300s clock skew
4. expiry not in past
5. TTL ≤ 86400s
6. canonical encoding

None of these checks bind the advertisement to the **current TCP connection**.
A captured advertisement is replayable until its `expiry` (up to 24h later).

The dashboard, the architecture test #25, and the spec/04 §3.2 claim all
describe this as "authenticated directed link" — **this is a false claim**
and must be retracted (see corrective work item F7).

## What the repair MUST prove

Per spec/04 §3.2 the legal link-creation pipeline is:

```text
advertisement → candidate endpoint → transport connection →
peer authentication → LinkUp
```

The "peer authentication" step must prove **fresh possession of the signing
key bound to the connection transcript**. Concretely, each side must sign
a transcript that includes:

1. A fresh **challenge nonce** generated by the verifier (not the signer).
2. The **direction** of the challenge (who issued it, who is responding).
3. A **transcript hash** binding all prior handshake messages in this
   connection (so the signature cannot be replayed in a different
   connection with different messages).
4. The **LinkId** being established (so the possession proof is bound to
   the specific directional link, not just the peer identity).

## What this ADR does NOT specify (deferred to a follow-up implementation ADR)

This ADR is a **proposal to define the repair**, not the repair itself.
Once the Principal Architect approves the framework below, a follow-up
ADR will specify:

- The exact transcript-CBOR schema
- The exact domain-separation string (e.g. `sharenet-link-possession-v1`)
- The exact signature input (transcript hash + challenge + direction + LinkId)
- Replay rules (nonce uniqueness, window size, storage requirements)
- Failure handling (what happens when challenge verification fails mid-handshake)
- Test vectors (a valid transcript signature, an invalid one, a replayed one)
- Wire-format changes (does the handshake become 4 messages? does it add
  a `PossessionProof` field to the existing InitiateMessage/AcceptMessage?)

## Proposed repair framework (for approval)

```text
Initiator (A)                       Responder (B)
-----------                         -------------
1. SEND InitiateMessage{
     advertisement: adv_A,
     challenge_for_B: nonce_A→B       // A generates a challenge for B to sign
   }                              →
                                    2. verifyAdvertisement(adv_A)
                                       IF FAIL → RejectMessage, close
                                       IF OK → sign possession proof:
                                         sig_B = Ed25519.sign(
                                           "sharenet-link-possession-v1"
                                           ‖ transcript_hash_so_far
                                           ‖ LinkId(local=B, remote=A, nonce_A→B, nonce_B→A)
                                           ‖ challenge_for_A   // B generates a challenge for A
                                           ‖ direction=RESPONDER
                                         )
                                       SEND AcceptMessage{
                                         advertisement: adv_B,
                                         challenge_for_A: nonce_B→A,
                                         possession_proof: sig_B
                                       }
   ←
3. verifyAdvertisement(adv_B)
   verify sig_B against adv_B.signingPublicKey over the transcript
   IF FAIL → close, no LinkUp
   IF OK → sign A's possession proof:
     sig_A = Ed25519.sign(
       "sharenet-link-possession-v1"
       ‖ transcript_hash_so_far
       ‖ LinkId(local=A, remote=B, nonce_A→B, nonce_B→A)
       ‖ challenge_for_B
       ‖ direction=INITIATOR
     )
     SEND PossessionConfirm{ proof: sig_A }  →
                                       4. verify sig_A against adv_A.signingPublicKey
                                          IF FAIL → close, no LinkUp (record audit)
                                          IF OK → LINK_UP (both sides)
```

The handshake grows from 2 messages to 3 (adding `PossessionConfirm`).
Alternatively, the possession proofs can be embedded in the existing 2
messages if the initiator's challenge is pre-announced — but this
complicates the transcript binding. The 3-message form is cleaner.

## Replay rules (proposed)

- Each `nonce_X→Y` is 16 bytes, cryptographically random, single-use.
- The responder MUST reject any AcceptMessage whose `challenge_for_A`
  matches a previously-seen challenge (replay window: 5 minutes).
- The initiator MUST reject any `sig_B` that does not verify against
  the transcript hash it computed locally (transcript binding).
- Both sides MUST reject any `possession_proof` whose `direction` field
  does not match their role in this connection.
- On any verification failure, the socket is closed immediately and a
  `LINK_DOWN` event with `reason="possession_proof_failed"` is recorded.

## Failure handling (proposed)

- Verification failure of `sig_B` (responder's proof): initiator closes
  socket, records `LINK_DOWN` with reason, increments an
  abuse-detection counter for the peer's NodeId.
- Verification failure of `sig_A` (initiator's proof): responder closes
  socket, records `LINK_DOWN` with reason, increments abuse counter.
- Three failures within 60 seconds from the same peer NodeId: the
  peer is added to a temporary denylist (5 minutes) and future
  connection attempts from that NodeId are refused at the TCP layer.

## Test vectors required (to be authored in the follow-up ADR)

1. A valid 3-message handshake producing LINK_UP on both sides.
2. A replayed `AcceptMessage` (captured from a prior connection) — MUST
   fail transcript binding (the transcript hash differs because
   `nonce_A→B` differs).
3. A tampered `possession_proof` (one bit flipped) — MUST fail signature
   verification.
4. A `direction` field swap (initiator claims RESPONDER) — MUST fail.
5. A `LinkId` mismatch (proof signed over a different LinkId) — MUST fail.

## Decision required from the Principal Architect

Choose exactly one:

1. **APPROVE the 3-message framework above** and authorize a follow-up
   implementation ADR with exact wire format + test vectors.
2. **APPROVE a variant** (specify: 2-message with embedded proofs?
   different transcript binding? different replay window?).
3. **REJECT the framework** and require a different approach (specify).
4. **DEFER** — keep the current 2-message exchange but relabel it
   everywhere as "advertisement-verification exchange" (not
   "authenticated link") until a formal security review is complete.

Until the Principal Architect decides, the current code, spec/04, ADR-0014,
the dashboard, and architecture test #25 must be **truthfully relabeled**
to reflect that the exchange verifies advertisements but does NOT prove
fresh key possession.

## What this ADR does NOT do

- Does NOT change any code.
- Does NOT modify the handshake wire format.
- Does NOT add test vectors.
- Does NOT proceed to routing, circuits, gateway forwarding, Android, or any other protocol work.
